# 版本号与版本文件

## 目标

1. 版本号只有一个声明处，构建时自动使用，不再散落在命令里。
2. 每做一次改动就在当前最新版本上把小版本 +1，不管这次改动属于哪一版的需求。

## 版本号规则

版本号形如 `0.20.0-seamless-vX.Y.Z`：

| 部分 | 含义 | 变化时机 |
| --- | --- | --- |
| `0.20.0` | 上游基线版本 | 跟随上游升级 |
| `vX.Y` | 定制的主线版本 | 有新需求时变，对应 SPEC.md 里的一节 |
| `Z` | 补丁号 | 每做一次改动 +1 |

例：主线停在 `v0.7` 时，

| 改动 | 版本号 |
| --- | --- |
| 媒体库显示设置崩溃的修复 | `0.20.0-seamless-v0.7.1` |
| 修的是 `v0.5` 时期的问题 | `0.20.0-seamless-v0.7.2` |
| 又一处修改 | `0.20.0-seamless-v0.7.3` |

修旧版本的需求不会回到旧版本上开分支，一律在当前最新版本上递增。

本次改动本身是「版本号设计」这条需求，因此主线版本走到 `v0.8`，`version.properties` 里写的是 `0.20.0-seamless-v0.8`。
上一条需求（继续观看补写的时区修正）落在主线还是 `v0.7` 的时候，版本号是 `v0.7.1`。

## 执行步骤

1. 新增仓库根目录的 `version.properties`，里面声明 `jellyfin.version`。
2. `buildSrc/src/main/kotlin/VersionUtils.kt` 的 `getVersionName` 增加一个来源：Gradle 属性 `jellyfin.version`、环境变量 `JELLYFIN_VERSION` 之后，读根目录的 `version.properties`。
3. `Makefile` 的 `VERSION` 改为从 `version.properties` 读取，环境变量与命令行参数仍可覆盖。
4. `SPEC.md` 记录版本号约定与 TODO。

## 版本号的来源顺序

| 优先级 | 来源 | 用途 |
| --- | --- | --- |
| 1 | `-Pjellyfin.version=...` | 命令行临时指定 |
| 2 | 环境变量 `JELLYFIN_VERSION` | CI 与脚本 |
| 3 | `version.properties` | 仓库里声明的正式版本号 |
| 4 | `0.0.0-dev.1` | 兜底 |

## 验证

```shell
make version                              # 0.20.0-seamless-v0.8
JELLYFIN_VERSION=9.9.9-test make version  # 9.9.9-test
make version VERSION=1.2.3               # 1.2.3
make build                                # 产物名带同一个版本号
```

直接跑 `./gradlew assembleRelease`（不带 `-Pjellyfin.version`）产出的也是 `jellyfin-androidtv-v0.20.0-seamless-v0.8-release.apk`。

## 附录

### 补丁号不会影响覆盖安装

`app/build.gradle.kts` 的 `versionCode` 取 `maxOf(getVersionCode(versionName), 200_100)`。
上游的 `getVersionCode` 从预发布部分取「最后一个点号后的数字」，`seamless-v0.7.1` 解析不出数字时统一取 99，
因此定制版本的 versionCode 一直是 200_100，补丁号变不变都是同一个值。
Android 只在 versionCode 变小时拒绝安装，相同值允许覆盖，所以补丁号递增不会让覆盖安装失败。

### 为什么版本号放在 properties 文件而不是 gradle.properties

`gradle.properties` 会被 Gradle 直接读成项目属性，版本号放进去之后 `./gradlew assembleRelease` 也能生效，
但那个文件是上游用于配置 SDK 版本的，`version.properties` 单独一个文件更清楚，也不会和上游配置混在一起。
