# v0.6 继续观看 与 v0.7 播放性能

## 目标

v0.6：首页「继续观看」显示的条目与时间点，必须是用户最近实际在看的这一集。

v0.7：按键到画面响应之间不再有等待；削减播放期间的周期性主线程开销；同时加日志，为真机实测定位「卡顿」到底在解码还是缓冲。

## 根因分析

服务端的「继续观看」完全由用户数据决定，客户端是唯一能影响它的一方：

- `ItemsController.GetResumeItems` 用 `IsResumable=true` 与 `OrderBy=DatePlayed Desc` 取条目；`OrderMapper.MapOrderByField(DatePlayed)` 实际的排序键是 `MAX(UserData.LastPlayedDate)`。
- 入选条件是 `UserData.PlaybackPositionTicks > 0`；`UserDataManager.UpdatePlayState` 会把低于 `MinResumePct` 的进度清零；`SessionManager.OnPlaybackProgress/Stopped` 每收到一次带位置的报告就刷新一次 `LastPlayedDate`。

由此，「继续观看停在第三季某一集」只有三种成因，且全都在客户端上报链路上：

1. **上报的位置不是真实位置**：待执行的快进把「跳转目标」当成当前位置上报，服务端存下的时间点会超前一个快进步长。
2. **正在看的那一集进度没进服务端**：投影仪直接断电时没有机会上报停止，或服务端按 `MinResumePct` 把位置清零，「继续观看」里就只剩更早弃看的旧集。
3. **「点开又退出」写了一条假进度**：客户端把继承来的旧续播点当成新进度上报，服务端刷新了那条旧记录的 `LastPlayedDate`，旧集因此顶到列表最前。

修复方向：不接管服务端的排序（排序继续由服务端按最后上报时间决定），而是让客户端上报的条目、位置、时间真实且自愈，服务端的数据自然就是对的。

## 执行步骤

1. 新增 `app/src/main/java/org/jellyfin/androidtv/ui/playback/PlaybackSessionProgress.kt`，记录本次会话的条目、起点与累计真实观看时长，只有相邻两次位置观测的正向增量才计入，继承来的旧位置不计入；观看不足 5 秒的会话不算「看过」。
2. `PlaybackController` 增加上报专用的取值 `getReportPositionMs()`：播放器在跑就用播放器的真实位置，播放器还没就绪才回退到 seek 目标（回退是必须的，否则会把服务端已有的续播点清零）。进度、暂停、停止三类报告统一改用它。
3. `PlaybackController` 的进度上报与停止上报按会话门限处理：没达门限的会话不产生进度；从已有续播点进入且没达门限时，停止上报直接不发，不动服务端原有数据；从头开始且没达门限时停止上报位置 0（服务端本来也没有位置）。暂停上报保持原样，它是用来保住服务端会话的。
4. 新增 `app/src/main/java/org/jellyfin/androidtv/ui/playback/LastPlaybackStore.kt`，在上报成功后把「条目 id + 位置 + 时间」落到本地 SharedPreferences。
5. 新增 `app/src/main/java/org/jellyfin/androidtv/ui/playback/ResumeProgressSync.kt`：`ResumeProgressDecision` 是纯逻辑的校正决策，`ResumeProgressSync` 负责查服务端的条目状态并用 `updateItemUserData` 把续播位置直接写回服务端（绕开服务端的 `MinResumePct` 判定），同时带上最后播放时间，服务端的排序才会把它排在最前。
6. `ItemRowAdapter.retrieveResumeItems` 在拿到服务端的列表后做一次校正，需要补写时补写并重新拉取这一行。
7. `PendingSkip.request()` 返回「本次请求是否开启新手势」，`PlaybackController.skip()` 据此决定立即跳转：首次按键立刻 seek，手势基准保持不变，后续按键继续合并到同一次跳转，原有「缓冲期不丢请求、每 200ms 重试」的逻辑不动。
8. `CustomPlaybackOverlayFragment.startFadeTimer()` 不再每次按键都重设窗口布局与系统栏状态，这两件事在播放页进入时已经做过；`setCurrentTime` 只在控制条可见时更新 Leanback 的进度条与播放状态，分段提示的位置只在提示出现时更新，控制条出现时补一次位置刷新。
9. `VideoManager` 记录缓冲次数与累计时长、丢帧数，`PlaybackController` 记录播放方式、码率与分辨率，供真机实测判断卡顿来源。
10. `ReportingHelper` 的上报日志补上条目 id、季集与位置，`PlaybackController` 的停止日志同样带上会话实际观看的时长。

## 最终方案

| 场景 | 行为 |
| --- | --- |
| 正常观看 | 每 3 秒上报一次真实播放位置，服务端的「继续观看」按最后播放时间排序 |
| 快进待执行时 | 上报播放器的真实位置，不再把跳转目标当成当前位置 |
| 点开一集就退出 | 不产生续播点，也不刷新旧条目的最后播放时间 |
| 从已有续播点进入又退出 | 服务端原有的续播点保持不变 |
| 服务端丢掉了最近观看的进度 | 首页加载「继续观看」时把位置补写回服务端，该条目重新排在最前 |
| 单击快进快退 | 立即跳转，不再等待合并窗口 |
| 长按快进快退 | 首次立即跳，后续按键在 800ms 窗口内累加，松手后跳到最终位置 |
| 控制条隐藏时 | 不再每 500ms 刷新进度条与播放状态 |

## 投影仪实测要点（由用户手动触发时执行）

1. 看第四季那一集，中途直接关投影仪；重新开机后首页「继续观看」应显示第四季那一集与正确时间点。
2. logcat 过滤 `Report progress`、`Report stop`、`Resume sync`，核对上报的条目 id、季集、位置与补写结果。
3. 单击右键应立即跳 30 秒（不再等 800ms）；长按仍按按键次数累加。
4. 播放卡顿：看 `Player is buffering` 与 `Dropped ... video frames` 日志，判断是解码瓶颈还是网络缓冲。

## 附录

### 备选方案与取舍

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 客户端重排「继续观看」 | 用本地最近观看记录把条目提到第一位 | 未采用。用户要求排序完全信任服务端，改为让服务端数据正确 |
| 清理旧集的服务端续播点 | 看完新一集时把同剧旧集的续播点清零 | 未采用。属于破坏性写服务端数据，用户未授权 |
| 缩短快进合并窗口到 300ms | 不改模型，只缩短等待 | 未采用。首次立即跳加后续合并的体感更好且不牺牲长按语义 |
| 每次按键都立即跳转 | 最跟手 | 未采用。长按会连续触发多次 seek，播放器反复缓冲 |
| 调大默认缓冲长度 | 缓解卡顿 | 未采用。用户要求不改可配置的播放参数，只改代码开销并加日志 |
| 「没看就退出」时清零旧续播点 | 停止上报位置 0 | 部分采用。从头开始时上报 0，从已有续播点进入时保留服务端原值 |

### 服务端规则摘录（判断依据）

- `ItemsController.GetResumeItems`：`IsResumable=true`、`OrderBy=DatePlayed Desc`、`Recursive=true`，取的是叶子条目。
- `BaseItemRepository.TranslateQuery` 的 `IsResumable`：叶子条目等价于 `UserData.PlaybackPositionTicks > 0`。
- `OrderMapper.MapOrderByField(DatePlayed)`：排序键是 `MAX(UserData.LastPlayedDate)`。
- `UserDataManager.UpdatePlayState`：低于 `MinResumePct` 清零位置，高于 `MaxResumePct` 标记为已看完。
- `SessionManager.OnPlaybackProgress/OnPlaybackStopped`：每次带位置的报告都会刷新 `LastPlayedDate`；`UpdatePlayState` 把位置清零时不刷新。
- `ItemsApi.updateItemUserData` 直接写 `PlaybackPositionTicks`，不经过上面的百分比判定，是断点校正能生效的原因。

### 会话门限取 5 秒的原因

服务端按播放位置判定是否保留续播点，客户端按本次会话实际推进的距离判定是否上报，两者含义不同：会话从旧续播点开始时，服务端看到的是很大的绝对位置，客户端看到的是这次实际看了多久。门限取 5 秒，是要区分「点开就走」和「真的在看」，又不至于让正常观看的前几秒白等。
