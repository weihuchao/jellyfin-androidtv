# v0.5 长按快进快退

## 目标

让长按快进或快退时用户按的每一次都算数：缓冲期间的按键不再被丢弃，长按过程中屏幕上有实时的快进提示。

## 背景

改动前的快进快退逻辑集中在 `PlaybackController`，长按一次遥控器的快进键会重复触发 `skip()`，而请求在三个地方被丢弃：

1. `skip()` 的守卫是 `hasInitializedVideoManager() && (isPlaying() || isPaused()) && spinnerOff && ...`。seek 之后 ExoPlayer 会重新缓冲，此时 `exoPlayer.isPlaying()` 为 false（`VideoManager.isPlaying()` 直接透传 ExoPlayer），这一期间的按键会被整个忽略，目标位置根本没记上。
2. `skipRunnable` 的第一行是 `if (!(isPlaying() || isPaused())) return;`，缓冲期直接丢弃已经累计的目标位置，而且不把 `currentSkipPos` 清零，下次继续在旧基准上累加，位置会越跳越偏。
3. `seek()` 在 `wasSeeking` 为真时直接 return，后续的跳转请求被静默丢弃，只留下一条 `Timber.d` 日志。

结果是长按快进的体验很差：第一次跳完开始缓冲，缓冲期间再按的几次全部蒸发，松手后只跳了第一段，位置和按键次数对不上。而且整个长按过程中画面完全不动（此时控制条是隐藏的），用户没有任何反馈。

## 执行步骤

1. 新增 `app/src/main/java/org/jellyfin/androidtv/ui/playback/PendingSkip.kt`，保存本次手势的基准位置、累计目标位置与累计偏移量。
2. `PlaybackController` 用 `PendingSkip` 替换原来的 `currentSkipPos` 字段。
3. `skip()` 去掉 `(isPlaying() || isPaused())` 守卫，缓冲期间的请求也记录下来。
4. `skipRunnable` 不再丢弃请求，改为每 200ms 重试一次，直到播放器恢复播放或暂停、且上一次的跳转已经落地。
5. `refreshCurrentPosition()` 里 `wasSeeking` 的复位移出分支，否则存在待处理的快进时它永远清不掉，后续跳转一直被 `seek()` 拒绝。
6. `stop()` 时清掉待处理的快进并撤掉重试回调。
7. 新增 `SkipIndicatorView`（Compose），显示快进快退的方向与累计偏移量，1 秒无新请求后淡出。
8. 在 `vlc_player_interface.xml` 里挂上这个视图，`PlaybackController.skip()` 每次请求后通知播放页。

## 最终方案

| 场景 | 行为 |
| --- | --- |
| 缓冲期间按快进快退 | 请求被记下，播放器恢复后立即执行，不再丢失 |
| 长按快进 | 右下角显示「快进 N 分钟」，偏移量随按键累加；松手后一次跳到最终位置 |
| 长按快退 | 右下角显示「快退 N 分钟」，同上 |
| 单击快进快退 | 跳 30 秒 / 10 秒，行为不变；也会闪现一次提示 |
| 播放器停止或出错 | 待处理的快进被清掉，不再重试 |
| 合并窗口 | 仍是 800ms，长按仍是松手后跳一次 |

## 附录

### 三处丢弃的成因

- `VideoManager.isPlaying()` 直接返回 `mExoPlayer.isPlaying()`，ExoPlayer 在缓冲期的状态是 `STATE_BUFFERING`，`isPlaying()` 为 false。`PlaybackController.isPlaying()` 又要求 `mPlaybackState == PLAYING`，所以缓冲期两道守卫都不成立。
- `skipRunnable` 丢弃目标时不重置 `currentSkipPos`，下一次 `skip()` 会继续在旧基准上累加，位置会越来越偏。
- `seek()` 的 `wasSeeking` 分支只打日志就返回，调用方无从得知请求被丢了。

### wasSeeking 的死结

`wasSeeking` 表示「上一次跳转还没落地」，由 `refreshCurrentPosition()` 在播放器恢复播放时复位。但该方法里 `wasSeeking = false` 原本写在 `currentSkipPos == 0` 的分支内，而待处理的快进期间 `currentSkipPos` 一直非零，于是 `wasSeeking` 永远清不掉，`seek()` 就会一直拒绝新的跳转。修复后复位放在分支之外：播放器处于播放状态即视为上一次跳转已经落地，同时置位 `finishedInitialSeek`，否则 `mSeekPosition` 会永远停在跳转目标上，进度条和上报位置都会跟着错。

### keepCurrentPosition

原来的 `currentSkipPos` 还被用来做一件与快进无关的事：跳到片尾时要让 `mCurrentPosition` 停在总时长，这样上报给服务器的结束位置才正确。现在这个职责交给独立的 `keepCurrentPosition` 标志，`stop()` 时复位。

### 备选方案与取舍

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 长按期间画面连续前进 | 用倍速播放代替跳转 | 未采用。会破坏「每次跳 30 秒」的语义，且倍速下前进距离与按键次数对不上 |
| 长按期间按固定节奏分段跳 | 保留步进语义，画面一段段往前 | 未采用。每次跳转都要重新缓冲，反而更卡 |
| 缩短合并窗口让单击立刻响应 | 800ms 改小 | 未采用。会改变长按的交互模型，且效果取决于遥控器的按键重复间隔 |
| 保留合并窗口，把丢弃改成排队 | 交互模型不变，只修丢请求 | 采用 |
| 加屏幕提示 | 填补长按期间无反馈的空白 | 采用 |
| 提示做成控制条的一部分 | 复用现成 UI | 未采用。长按时控制条是隐藏的，提示必须独立于控制条 |

### 实现细节

- `PendingSkip` 用独立的 `pending` 标志而不是靠目标位置是否为 0 判断，因为快退到片头的目标位置正好是 0，那也是一个有效的待执行跳转。
- 提示浮层由 `skip()` 统一触发，所以控制条上的快进按钮、进度条上的左右键、遥控器的快进快退键都会显示提示，行为一致。
- 提示文案复用已有的 `R.string.fast_forward`、`R.string.rewind` 与 `R.plurals.minutes/seconds/hours`，没有新增字符串，也不需要动翻译文件。
- `SkipIndicatorView` 沿用 `SkipOverlayView` 的写法：右下角圆角胶囊、图标加文字、淡入淡出、1 秒无新请求后隐藏。
