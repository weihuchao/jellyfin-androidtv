# 继续观看补写的时区与账号

## 现象

用 molan 账号时，首页「继续观看」显示的集数与实际进度不一致：看到的是「火影忍者 S03E21」，实际进度在 S04E40。
在网页端把 S04E40 点成「标记已观看」也没有变化。

## 服务端数据核查

以下数据来自服务端接口（`GET /Users/{id}/Items/Resume`、`GET /Users/{id}/Items/{itemId}`、`GET /Shows/NextUp`），账号 molan。

| 条目 | 服务端记录 | 说明 |
| --- | --- | --- |
| S03E21 | `PlaybackPositionTicks=0`、`PlayCount=0`、`Played=false`、**没有 LastPlayedDate** | 服务端从未为这一集保存过有效续播点，也没有「看过」记录 |
| S04E40 | `PlayCount=2`、`LastPlayedDate=2026-11-13T06:40:02Z`、`Played=false`、`PlaybackPositionTicks=0` | 14:40 被看完（服务端标记已看完并清零位置），之后在网页端又被点了一下，变回「未观看」 |
| 「继续观看」列表 | 只有「火影忍者」「Season 3」「Season 4」三个容器条目 | 没有任何一集有续播点 |
| `Filters=IsResumable`（网页端口径） | 空 | 网页端「继续观看」现在也是空的 |
| `GET /Shows/NextUp` | 火影忍者 S04E40 | S04E40 现在是「未观看」，所以它是下一集 |

由此得出三条结论：

1. **被看完的一集不会出现在「继续观看」里**。服务端只保留有续播点（位置大于 0）且未看完的条目，所以「进度在 S04E40」和「继续观看里有 S04E40」本身是矛盾的。
2. **S03E21 不可能是服务端返回的条目**。服务端只有在收到带位置的播放上报时才会写 LastPlayedDate；位置低于最小续播百分比时只清零位置、不刷新时间。S03E21 没有任何时间戳，说明它从未有过有效续播点。
3. **网页端的「标记已观看」是开关**。S04E40 本来已经是「已观看」，再点一下就变回「未观看」（`Played=false`、`PlayCount` 加一），对「继续观看」没有任何影响。

## 根因

客户端补写续播点的判断用错了时区口径。

- SDK 把服务端返回的时间转成**设备本地时区**：`org.jellyfin.sdk.model.serializer.DateTimeSerializer` 的反序列化是 `ZonedDateTime.parse(value).withZoneSameInstant(ZoneId.systemDefault()).toLocalDateTime()`。
- 补写判断却把本地记录的时间转成 **UTC 的钟面时间**再比较：`playback.timestamp.atOffset(ZoneOffset.UTC).toLocalDateTime()`。

两者相差一个时区偏移（设备在东八区就是 8 小时），结果是：只有当本地记录的条目比服务端最新条目新 8 小时以上时才会触发补写。
真实场景里服务端留下的旧条目往往只比断电前的新条目早几分钟到几小时，正好落在偏差之内，补写不会发生，服务端那条旧条目继续排在「继续观看」的第一位，这就是「显示的集数不对」。

上一次真机实测之所以通过，是因为断电前后的条目相差超过 8 小时，恰好绕开了这个偏差。

## 执行步骤

1. `ResumeProgressDecision.needsRestore` 增加 `zone` 参数，把本地记录的时间转成设备本地时区后再与服务端时间比较，与 SDK 的口径一致。
2. `LastPlayback` 与 `LastPlaybackStore` 记录账号 id，`ReportingHelper` 上报时一并写入；补写前校验账号，别的账号看过的条目不写进当前账号。
3. 补写前校验位置，位置为 0 不补写：写 0 会把服务端已有的续播点清掉，并刷新最后播放时间。

## 附录

### 服务端接口行为实测（账号 weihc）

| 请求 | 结果 |
| --- | --- |
| `POST /Users/{id}/Items/{itemId}/UserData` 写位置 + 时间 | 位置与时间都写入，时间按服务端自己的时区回显 |
| 同上，只写位置 0 | 位置清零，`LastPlayedDate` 保留 |
| 同上，写位置 0 + 时间 | `LastPlayedDate` 被刷新，条目因位置为 0 不再出现在「继续观看」 |
| 同上，只写位置，不带时间 | 位置写入，时间保持原值 |

### 排查用到的服务端接口

| 接口 | 用途 |
| --- | --- |
| `GET /Users/{id}/Items/Resume` | 「继续观看」列表，排序键是最后播放时间 |
| `GET /Users/{id}/Items?Filters=IsResumable&IncludeItemTypes=Movie,Episode` | 网页端「继续观看」的口径，只含有续播点的叶子条目 |
| `GET /Users/{id}/Items/{itemId}` | 单个条目的用户数据（位置、是否看完、最后播放时间、播放次数） |
| `GET /Shows/NextUp?UserId={id}` | 「下一集」列表 |

### 服务端时间戳的三种写法

同一个字段的格式能看出是谁写的：

| 格式 | 写入方 |
| --- | --- |
| `2026-11-13T03:10:42.5903917Z` | 服务端自己写的（7 位小数 + Z） |
| `2026-11-13T05:16:33.574+00:00` | 客户端用 `updateItemUserData` 补写的（SDK 按设备时区带偏移） |
| `2026-11-13T06:00:00.0000000Z` | 直接用不带时区的字符串写入的（服务端按 UTC 理解） |

### 未采用的方案

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 客户端重排「继续观看」 | 用本地记录把条目提到第一位 | 未采用，用户要求排序完全信任服务端 |
| 清理旧集的服务端续播点 | 看完新一集时把同剧旧集的续播点清零 | 未采用，属于破坏性写服务端数据，用户未授权 |
| 不发开始上报 | 避免服务端在会话断开时刷新最后播放时间 | 未采用，代价是服务端在前几秒不知道有播放会话 |
